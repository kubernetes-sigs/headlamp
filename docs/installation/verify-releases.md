Use release signatures to verify the origin and integrity of Headlamp downloads.
The sections below describe the verification material available for each
artifact type.

Release checksums, container images, and newer Helm charts use
[Sigstore](https://www.sigstore.dev/) keyless signing in the GitHub Actions
release workflows. Signed source tags use maintainer signing keys, and Helm chart
packages also have GPG signatures.

New desktop app and Helm chart releases also include [SLSA](https://slsa.dev/)
provenance, which records the GitHub Actions workflow, branch or tag, and commit
that built them. Provenance is also stored in GitHub's attestation API, so it
can be checked with the [GitHub CLI](https://cli.github.com/).

Release checksum and container signatures are available from v0.46.0.
For earlier releases, checksum comparison detects corruption but does not
authenticate the download because the checksum manifest is unsigned.
App provenance and Helm Sigstore bundles are available in their respective
releases after 0.46.0, as detailed below. Signatures and provenance are separate:
verifying a signature does not require a SLSA provenance bundle.

The cosign commands on this page need
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) v2.6.3
or later, because older versions cannot read the signature format that Headlamp
releases use.

## Desktop apps and binaries

[App releases](https://github.com/kubernetes-sigs/headlamp/releases) from
v0.46.0 include:

- `checksums.txt`: the SHA-256 checksums of the release's apps and binaries.
- `checksums.txt.sigstore.json`: a Sigstore signature bundle for
  `checksums.txt`.

App releases after v0.46.0 additionally include `headlamp-X.Y.Z.intoto.jsonl`:
SLSA provenance for the files listed in `checksums.txt`.

To verify a download, first verify `checksums.txt`. It is signed by the release
assets workflow running from the `main` branch:

```shell
cosign verify-blob checksums.txt \
  --bundle checksums.txt.sigstore.json \
  --certificate-identity 'https://github.com/kubernetes-sigs/headlamp/.github/workflows/push-release-assets.yml@refs/heads/main' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Then check the files you downloaded against it:

```shell
sha256sum --check --ignore-missing checksums.txt
```

On macOS, use `shasum -a 256 --check --ignore-missing checksums.txt`. On
Windows, use PowerShell (replace the file name with the one you downloaded); it
prints `True` if the checksum matches:

```powershell
$file = 'Headlamp-X.Y.Z-win-x64.exe'
$expected = (Select-String -Path checksums.txt -Pattern "  $file`$").Line.Split(' ')[0]
(Get-FileHash -Algorithm SHA256 $file).Hash -eq $expected
```

The macOS app is also signed and notarized by Apple, so macOS verifies it at
install time. For Windows installers, use the signed checksum verification
above; Authenticode signatures are not currently provided.

To check the provenance of a download, which was generated by the app build
workflows:

```shell
gh attestation verify Headlamp-X.Y.Z-linux-x64.AppImage \
  --repo kubernetes-sigs/headlamp \
  --bundle headlamp-X.Y.Z.intoto.jsonl \
  --cert-identity-regex '^https://github\.com/kubernetes-sigs/headlamp/\.github/workflows/app-artifacts-(linux|mac|win)\.yml@'
```

The output shows the workflow and the branch or tag that it built. Without
`--bundle`, `gh` fetches the provenance from GitHub instead.

## Container images

Release images at `ghcr.io/headlamp-k8s/headlamp` are signed when they are built
from a release tag, and come with build provenance attestations:

```shell
cosign verify ghcr.io/headlamp-k8s/headlamp:vX.Y.Z \
  --certificate-identity-regexp '^https://github\.com/kubernetes-sigs/headlamp/\.github/workflows/container-publish\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The `nightly` image is signed by scheduled builds from `main` or manual builds
from a selected branch. Both publish to the same `nightly` tag. To verify an
image built from `main`:

```shell
cosign verify ghcr.io/headlamp-k8s/headlamp:nightly \
  --certificate-identity 'https://github.com/kubernetes-sigs/headlamp/.github/workflows/nightly-build.yml@refs/heads/main' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

For a manual build from another branch, replace `refs/heads/main` in the
certificate identity above with `refs/heads/<selected-branch>`.

## Helm chart

Chart releases on GitHub (`headlamp-helm-X.Y.Z`) include the chart package,
`headlamp-X.Y.Z.tgz`, and a GPG `.prov` provenance file. Releases after 0.46.0
additionally include `headlamp-X.Y.Z.tgz.sigstore.json` (a Sigstore signature
bundle) and `headlamp-X.Y.Z.tgz.intoto.jsonl` (SLSA provenance).

The chart release workflow verifies the downloaded package against both published
bundles before reporting success for releases created from that workflow's
commit, including reruns. This is a post-publication check: a failed run may
leave an incomplete release that needs attention. Releases from other commits
are left unchanged and reported as skipped, not verified; a skipped check does
not satisfy the release checklist. Release coordinators should also record an independent
verification using the commands below.

To verify the chart with cosign, download the chart and its signature bundle,
then check that it was signed by the chart release workflow running from the
`main` branch:

```shell
helm repo add headlamp https://kubernetes-sigs.github.io/headlamp/
helm pull headlamp/headlamp --version X.Y.Z
curl -LO https://github.com/kubernetes-sigs/headlamp/releases/download/headlamp-helm-X.Y.Z/headlamp-X.Y.Z.tgz.sigstore.json
cosign verify-blob headlamp-X.Y.Z.tgz \
  --bundle headlamp-X.Y.Z.tgz.sigstore.json \
  --certificate-identity 'https://github.com/kubernetes-sigs/headlamp/.github/workflows/helm-chart-release.yml@refs/heads/main' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

To check the chart's provenance, which was generated by the same workflow:

```shell
gh attestation verify headlamp-X.Y.Z.tgz \
  --repo kubernetes-sigs/headlamp \
  --cert-identity 'https://github.com/kubernetes-sigs/headlamp/.github/workflows/helm-chart-release.yml@refs/heads/main'
```

The GPG signature (key fingerprint
`2956 B7F7 1677 6937 0C93  730C 7264 DA7B 85D0 8A37`) can be verified with Helm:

:::note
The public key is not currently available from public keyservers (see
[#5093](https://github.com/kubernetes-sigs/headlamp/issues/5093)), so the
`gpg --recv-keys` command below fails until it is published.
:::

```shell
gpg --keyserver hkps://keys.openpgp.org --recv-keys 2956B7F7167769370C93730C7264DA7B85D08A37
gpg --export 2956B7F7167769370C93730C7264DA7B85D08A37 > headlamp-pubring.gpg
helm repo add headlamp https://kubernetes-sigs.github.io/headlamp/
helm pull headlamp/headlamp --verify --keyring headlamp-pubring.gpg
```

## Source code

Signed release tags can be verified using the release maintainer's signing key.
Some historical tags, including v0.44.0, are unsigned lightweight tags and
cannot be verified with `git tag -v`; obtaining a signing key does not change
that limitation. The instructions below apply only to signed tags.

Before trusting a signed tag, confirm the expected release maintainer and signing-key
fingerprint through a trusted project channel. This applies to both GitHub and
local verification; the tagger name and email are not themselves proof of
identity or authorization to sign Headlamp releases.

On [GitHub](https://github.com/kubernetes-sigs/headlamp/tags), the **Verified**
label means GitHub has verified the signature against a registered signing key.
Check the signature details against the project-confirmed signer and key; the
badge alone does not establish Headlamp release-signing authorization.

For SSH signatures, use keys registered for signing rather than treating an
authentication-key listing as a release-signing trust source. GitHub registers
these uses separately; see its
[SSH signing-key guidance](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account).

For local verification of SSH-signed tags, download candidate signing keys and
inspect their fingerprints first (replace `USERNAME` with the confirmed
maintainer's GitHub username):

```shell
curl --fail --silent --show-error https://api.github.com/users/USERNAME/ssh_signing_keys \
  --output signing-keys.json
jq -r '.[].key' signing-keys.json > candidate-signing-keys.pub
ssh-keygen -lf candidate-signing-keys.pub
```

Copy only the public-key line matching the independently confirmed fingerprint
into `release-signing-key.pub`. Do not add the entire candidate list to
`allowed_signers`. Replace `EMAIL` with the confirmed signer's email:

```shell
ssh-keygen -lf release-signing-key.pub
printf 'EMAIL namespaces="git" %s\n' "$(cat release-signing-key.pub)" > allowed_signers
git -c gpg.ssh.allowedSignersFile="$PWD/allowed_signers" tag -v vX.Y.Z
```

For GPG-signed tags, obtain a public-key file containing only the independently
confirmed signing key from the release maintainer's approved publication
channel. Inspect the primary-key and subkey fingerprints before importing that key:

```shell
gpg --show-keys --fingerprint --with-subkey-fingerprint release-signing-key.asc
```

After confirming the primary key and any signing subkey match the
project-confirmed fingerprints:

```shell
gpg --import release-signing-key.asc
git tag -v vX.Y.Z
```

Successful local verification must exit with status zero and match the expected
signer and independently confirmed fingerprint. A `Good "git" signature` message
followed by `No principal matched` is not successful verification.

:::note
For v0.45.0 and v0.46.0, GitHub currently reports `unknown_key`, and the signing-key lookup
above does not provide the matching key. Contact the release maintainer for a
confirmed historical signing key and verification route before trusting these
tags. Do not substitute another key to bypass a verification failure.
:::
